# SALES-1: synthetic local browser acceptance (24 September 2026)

This is a **local synthetic-book observation**, not production invoice, legal PDF, bank settlement, customer delivery or company acceptance. It supplements the [frontend journey ledger](../../frontend.md). No test files were added. Browser captures and a machine-readable, credential-free observation are in [sales1-local](sales1-local/observed.json). The `.cache` browser scripts used during the run are local-only; the steps below are the repeatable procedure.

## Reproduce

1. Follow [local development](../../local-development.md) against a **new disposable PostgreSQL 17 database**. Provision a synthetic SEK operator book, create a local sign-in, and start the API Worker and web app. Never use a company book or commit credentials. The observed fixed web checkout began at `312d5ba` and included the then-current `invoice-draft-session.tsx`, `invoice-payment-review.tsx`, and `invoice-payments.tsx` from the shared tree (`9093836`). Run `bun run check-types` and `bun run lint` there before browser work; both returned zero errors for this source set. After concurrent supplier work settled, the shared tree at `13502f7` also passed both full checks.
2. Sign in as the book operator. In **Sales**, create a draft with a customer and one positive line, edit and save it, open the issue review and use the explicitly synthetic issue path. Reload the registered invoice and inspect its document and payment stage. Do not present a synthetic issue as legal delivery.
3. Post synthetic manual journals into the invoice's receivables control account, with evidence and approved/committed change sets. For pagination, post at least 26 distinct eligible payment lines and match them to the invoice using the approved allocation flow. In the invoice's **Payments**, verify available-payment pages, matched-history page 2, direct-link reload and return to the same filtered register. Set `paymentPage=99` and `paymentHistoryPage=99` in the invoice URL; each must recover to page 1 rather than strand the user.
4. From an approved but unapplied allocation plan, consume the same payment line in another approved plan. Reload the first plan. It must say **This review has changed**, omit **Approved until**, and offer neither Approve nor Confirm. Separately, leave a current approved plan untouched until its actual `expiresAt` passes. With a fresh `Idempotency-Key`, try its expired approval in `POST /commerce/allocation-plans/{planId}/apply`: expect `403 ApprovalRequired`, unchanged dependencies and no application. Open the saved review in a freshly signed-in browser: it must show **Approval expired**, offer Approve and hide Confirm. Reapprove in the browser, then Confirm becomes available; do **not** commit the allocation. Retry the old approval ID with a fresh idempotency key: it must still return `403 ApprovalRequired`. A separate clock-shift screenshot is UI-only; it is not used as server-expiry evidence.
5. In two browser tabs edit the same draft; save one, then try to save the older edit. Review the recover/compare choices. Repeat with storage access denied and with corrupt retained bytes. Exporting corrupt bytes must preserve the stored record. Switch to a different actor with no membership and confirm the old book is not disclosed. A direct API read with a token for another book returned 403 in this run.
6. Issue a second synthetic invoice. Post a 5.00 SEK synthetic payment and match 2.00 SEK to the first invoice and 3.00 SEK to the second in **one** approved plan. Open the first invoice's payment history, choose **Undo this match**, enter a reason, review both affected invoices, acknowledge, approve and confirm. The plan must release both legs; no original journal posting is reversed or bank refund initiated. Reload both invoices and check their outstanding balances and the restored payment availability.
7. At a 320px viewport with reduced motion, open payments and inspect readable stacked rows and page width. Focus **Close invoice**, press Enter, and verify navigation returns to Sales. At a 1440px viewport, setting `document.documentElement.style.zoom = "200%"` gives a CSS-zoom proxy: inspect the payment view and close it by keyboard. This is **not** a native browser zoom assertion. For visual/reference scope, compare the synthetic document hierarchy with the [Midday reference note](wave2-invoice-ui-320.md); the comparison is qualitative, not pixel parity or legal design approval.
