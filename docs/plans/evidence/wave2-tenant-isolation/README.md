# Synthetic two-book authorization audit (2026-09-24)

Revision `f7a85df494efae15e5c08f059d9716c80df1f13b`. The actual local Wrangler Worker used the restricted `openerp_app` PostgreSQL 17 login. Two separately provisioned books (`entity_synthetic_a/book_synthetic_a` and `_b`) and distinct bearer operators were exercised. No real tenant, external provider, or production service was touched. `observations.json` contains only probe names, HTTP status/error codes, failure modes, and final B table counts; it contains no token or database password.

**Finding:** No cross-book read, mutation, or replay leak was observed in the covered requests. A token scoped to A received 403 for B's book URL, and 404 for B's real identifiers under A's URL. After denied requests, B still had one issue, one PDF, one delivery request, one approval, one provider-unknown attempt, one connector batch, zero supplier exports, and unchanged setup revision 1. The B operator could read each B record. Independent A/B requests using the same key produced distinct IDs; own-key replay returned the original record. A's legal issue with B's issue digest and A's PDF with B's capture digest were rejected as `StaleDependency`.

## Reproduce on disposable state only

1. In this checkout, create a **new** PostgreSQL 17 cluster on an unused local port using `initdb -A trust`, `pg_ctl start`, and `createdb`. Set `DATABASE_ADMIN_URL` to that isolated DB and run `bun run --cwd apps/api db:migrate`. Never use an existing database.
2. Make two copies of `examples/synthetic-book.json`. Suffix its `entity.id`, `book.id`, `actor.id`, `fiscalYear.id`, `periods[].id` and `accounts[].id` with `_a` or `_b`. Move the fiscal year and token expiry forward if needed. Set a distinct random `OPENERP_ACCESS_TOKEN` (32–512 characters) for each `bun run --cwd apps/api db:provision <manifest>` call. Do not log these tokens.
3. Set a random `OPENERP_RUNTIME_PASSWORD` and run `bun apps/api/scripts/self-host-role.ts`. Start `bunx wrangler dev --cwd apps/api --config wrangler.jsonc --local` on an unused local port with an **outside-repository** `--env-file` containing a restricted `openerp_app` `DATABASE_URL`, random `BETTER_AUTH_SECRET` and local `BETTER_AUTH_URL`. Use `Authorization: Bearer <book-specific token>` for HTTP `/api/v1/entities/:entityId/books/:bookId` calls. This audit never used the admin database login in the Worker.
4. For a full positive legal ID per book, render `legal-issue-template.sql` into a private temporary file for A, then B. Replace `__ENTITY__`, `__BOOK__`, `__ACTOR_ONE__`, `__ACTOR_TWO__`, `__ACTOR_THREE__`, `__PERIOD__`, `__TOKEN_ONE__`, `__TOKEN_TWO__`, `__TOKEN_THREE__`, `__ISSUE_DATE__` and `__DUE_DATE__`. Use a fresh random second/third token for each book, distinct operator IDs, the **current UTC issue date**, and a future due date within the manifest period. Execute only with `psql "$DATABASE_ADMIN_URL" -v ON_ERROR_STOP=1 -f <private rendered file>`. This is a synthetic SQL setup fixture, not a source of legal or customer facts. The template contains placeholders, not tokens.
5. Fetch each issue ID and digest from `openerp.ar_legal_issues` in the isolated DB. Through Worker HTTP POST `/commerce/legal-invoice-pdfs` with `issueId`, `issueDigest`, `rendererVersion: openerp-se-invoice-takumi-v2` and an idempotency key. B's returned capture ID/digest/artifact hash can be used in POST `/commerce/legal-deliveries` with a reserved `.invalid` email destination, `providerProfileKey: synthetic_local`, and a reason. A's token + A's URL + B's real ID must return 404 for GET PDF, PDF delivery history, GET delivery, approval, render, prepare using B's PDF, and attempts. A's token + B's URL must return 403. A and B can each use the same PDF and delivery key **with their own source IDs**; own-key replay preserves each result. The delivery attempt is recorded only as `provider_unknown` with `externalTrafficProven: false`; do not contact a provider.
6. For supplier lookup/export authorization, apply `supplier-preview-seed.sql` only to the disposable database. This valid wire-shape preview has a **synthetic nonexistent invoice**: it only proves scoped preview lookup and denial of cross-book export, not payment eligibility or a valid export. B GET `/commerce/supplier-payment-batches/payment_preview_b_scope_valid` returns 200; A GET under A's URL and POST `/.../payment_preview_b_scope_valid/export` return 404. The A/B `/commerce/supplier-payment-batches/eligibility` lists were 200 but empty. To prove live positive supplier eligibility/export, create a real independently accepted supplier invoice and reviewed payee in both books; this audit did not.
7. POST scoped `/bank-connector-consents` with book-specific `account_bank_a`/`account_bank_b`, `source_a`/`source_b`, and synthetic provider IDs. B's consent ID under A GET/revoke/ingest returns 404. B's `uncertain` empty connector batch is recoverable under B using its key, not under A. For the same key across books, use each book's unused `account_clearing_*` with distinct `source_clearing_*`; both consent IDs differ. POST `/company-setup` with different names and the same key under each own book; both return 200 and own replay is stable, while A GET/POST on B URL returns 403. Firm-level `/v1/companies` rejects book API tokens (403); it needs a human sign-in and was not exercised positively.
8. Capture only status, error code, object IDs and book-level row counts. Stop **only** the Worker and PostgreSQL cluster created for this audit; delete private rendered SQL, env files, manifests, raw credentials and temp DB. Do not use the retained `observations.json` as a credential store.

## Limits and probe interpretation

- `legal-issue-template.sql` calls real SQL workflows in an admin-owned disposable fixture to create synthetic identities, evidence, review and issue. It bypasses production identity provisioning. The legal policy and issued invoice do **not** establish legal, provider, or actual-company acceptance.
- `supplier-preview-seed.sql` directly inserts a wire-valid preview without supplier-invoice/verification dependencies. The first malformed synthetic preview yielded a B-owner 500; replacing that preview with the valid-shape one yielded B 200 and A 404. This was a **fixture error**, not a demonstrated product failure. Supplier eligibility/execution remains unproven.
- The two separately rendered PDF artifacts had the same SHA-256 because their synthetic invoice facts yielded identical bytes. The captures had different scoped IDs and digests; identical content hashes are not tenant IDs. Mixing B's _capture digest_ into A's delivery returned 409 `StaleDependency`. A trial with B's artifact hash was not a wrong hash (the hashes were equal), so its 200 response is not a bypass.
- No provider account/credential, bank pull, customer email, bank submission, legal authority, MCP caller, browser session, hosted Worker, actual PDF visual quality, or real tenant was exercised. Source inspection found scoped `book_id` predicates and composite keys in the owning SQL functions, but this is a bounded HTTP/SQL observation, not a formal proof for every input or concurrency schedule.
- No product source, migration or test was changed by this audit. The placeholder SQL files here seed only disposable manual evidence; they are not production migrations. The [separate legal-delivery record](../wave2-legal-delivery-e2e/README.md) covers positive outbox lifecycle, not two-book authority.
