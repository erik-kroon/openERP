# Synthetic gross-cost supplier HTTP proof

Observed on 2026-09-24 with a disposable PostgreSQL 17 database, local Wrangler Worker, restricted `openerp_app` login and one synthetic operator. The [token-free request/response record](ap-gross-cost-http.json) contains the exact submitted bodies, statuses, IDs, journal lines and register result. Replace generated IDs, digests and idempotency keys with the values returned by each preceding call when repeating it; never reuse the captured tenant or database.

## Repeat

1. Provision a **new** disposable book and database by [local setup](../../local-development.md), with active bank, payable and expense accounts. Migrate through `8751-supplier-credit-source-tax.sql`; use the repo's current later migrations too. Start local Wrangler with the restricted database URL.
2. POST five evidence records and a supplier counterpart. POST a supplier draft with source number, evidenced identity/date/terms, exact line net `10000`, asserted tax `2500`, source gross `12500` and matching source total. POST `/commerce/supplier-acceptance-reviews` with `synthetic-gross-cost-supplier-v1`, current draft revision/digest and explicit payable/expense accounts. Approve and execute the exact review digest. GET the posted voucher and registered invoice.
3. POST a distinct credit source and `/commerce/supplier-credit-reviews` with `synthetic-gross-cost-supplier-credit-v1`, current invoice capacity, gross `2500` and asserted tax `500`. Approve and execute. GET its voucher; it must debit payable `2500`, credit expense `2500` and leave `10000` outstanding without a VAT account effect.
4. With a **different** credit source, request gross `3000`, tax `2100`: HTTP `422 InvalidJournal` because the committed source tax `500` plus requested `2100` exceeds the invoice's asserted `2500`. A tax assertion larger than gross also returns `422`. Do not approve any review prepared before the forward guard fix.
5. POST a separate synthetic manual payment journal with payment evidence: debit payable `4000`, credit bank `4000`. Approve and execute its plan digest. POST `/commerce/allocation-plans` using its posted payable line and the supplier invoice; approve and apply `4000`. GET invoice: gross `12500`, credited `2500`, allocated `4000`, outstanding `6000`. GET the three vouchers and compare their lines with the JSON record. The disposable database had one acceptance, one credit and one allocation receipt.
6. Stop only the Worker and database created for this proof. Do not submit a file to a bank.

The first excess-tax review **incorrectly succeeded** before forward `8751`, because the old guard read tax from the acceptance receipt instead of the sealed review. After applying `8751`, the identical public request with a new idempotency key returned `422`. No excess-tax credit was executed. The new acceptance/credit pair is synthetic gross cost only, not a deductible Swedish VAT treatment or a verified bank payment. Existing zero-tax behavior was separately observed in [the earlier HTTP run](ap-broader-local-http.md). No test files were added.
