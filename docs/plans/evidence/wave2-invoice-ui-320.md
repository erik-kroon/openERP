# Customer invoice editor: 320px browser check

Observed 2026-09-24 through the actual TanStack app with a disposable synthetic PostgreSQL book and local Worker, not a static component render. All owned processes were stopped. The isolated Worker supplied temporary `BETTER_AUTH_URL` and `BETTER_AUTH_SECRET`; the checkout's existing `apps/api/.dev.vars` has only `DATABASE_URL`, and without the temporary auth values `/api/auth/configuration` returned `503`. No real tenant data or dependency/test change was used.

## Repeat and inspect

Start a disposable synthetic book and local Worker as in [`docs/local-development.md`](../../local-development.md), with the restricted runtime database login and temporary auth values outside the checkout. Run the web app against that Worker. Sign in as the synthetic operator, open a draft invoice, choose **Edit draft**, then resize the browser viewport to 320px and capture the editor after fonts settle with reduced motion enabled. Tab from Edit draft through Refresh and disclosure controls, confirm visible focus, and use **Add line**. Check the viewport/document width and a separate issued invoice at 320px. Keep the old and new captures for a pixel comparison at a desktop width. Do not call a provider or use Drastic AB data.

The [before 320px editor](wave2-invoice-ui-320/editor-320-before.png) squeezed three date inputs into roughly 60px each; year values appeared as `20`. The [after 320px editor](wave2-invoice-ui-320/editor-320-after.png) stacks the three dates, so full `YYYY-MM-DD` values are visible. The change is one responsive grid prop in `apps/web/src/components/commerce/invoice-drafts.tsx`: `columns={3}` → `columnsAtSm={3}`. The [desktop before](wave2-invoice-ui-320/editor-desktop-before.png) and [desktop after](wave2-invoice-ui-320/editor-desktop-after.png) captures are pixel-identical. The [issued 320px view](wave2-invoice-ui-320/issued-320-after.png) remained in the viewport. At 320px, document width was 320px with no page horizontal overflow; the detailed line grid scrolls inside the editor. Tab focus was visible, reduced-motion preference was active, and **Add line** produced two removable rows without a page error.

A long title remains a single-line editable input that scrolls horizontally on focus; it is not fully visible at rest at 320px. The original Midday JPG references were absent from `/tmp` during this browser check. This record proves a local regression fix and accessibility observations, **not** exact Midday visual parity, actual-company invoice acceptance, or a browser test of external delivery.

Afterward, the original [Midday editor screenshot](https://raw.githubusercontent.com/midday-ai/midday/main/apps/website/public/images/update/invoice-pdf/invoice.jpg) and [PDF screenshot](https://raw.githubusercontent.com/midday-ai/midday/main/apps/website/public/images/update/invoice-pdf/pdf-invoice.jpg) were recovered from their public source for a qualitative visual comparison only; the images are not copied here. Both interfaces use a dark invoice drawer over a register and a restrained document layout with sender/recipient columns, an item table and lower totals. The synthetic Swedish legal PDF uses the same broad two-column/table/totals hierarchy, but does not reproduce the reference brand mark, QR code, typography or exact spacing. Such details require real reviewed seller identity, payment instructions and legal approval rather than a made-up Drastic AB document. This comparison is not pixel-parity proof.
