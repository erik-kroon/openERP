# Acceptance, independent examples and traceability

The existing [E-01–E-21 scenarios](../verification.md) remain the cross-cutting acceptance criteria. The area packet tables map each deliverable to those scenarios; the examples here make several expected outcomes concrete. These are planning records, not added test files or claims of execution. New test/fixture changes require applicable explicit authorization and must follow the repository's failure-first E2E approach.

## Independent scenario examples

All numbers below are **synthetic arithmetic fixtures**, not tax advice, market rates or approved company facts. The implementation must not calculate its own expected result and call that independent proof.

| Case                      | Given and action                                                                                                                                                                                                 | Expected durable result / decisive failure                                                                                                                                                                  |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

On success, retained original + exact reversal + replacement net to `9000`, with one aggregate correction outcome.                   |
| Competing first execution | Two live requests begin before either has committed, same key/input.                                                                                                                                             | One effect, one numbering outcome, same durable receipt. A different key for the same economic recognition cannot post another effect.                                                                      |
| Unknown outcome           | Allow commit, drop the response, reload the UI.                                                                                                                                                                  | Discovery/key recovery yields original receipt; no second posting. For domain rules, supplement these mechanics with independent source-reviewed positive/negative boundary cases: transaction-date changes, jurisdiction/registration changes, eligibility thresholds, partial deduction, irregular work schedules, historical rate/mapping changes and prior filings. These expected outputs must come from the selected primary evidence and domain review, not from an unreviewed answer set or the production calculator.

## Evidence artifact

An acceptance run records packet/scenario IDs; code/contract/migration/rule/validator versions; runtime/database versions; actor role and fixture scope without credentials; synthetic/actual-copy provenance and use authority; independently specified expected results; launch/drive/cleanup instructions; public responses; persisted receipts and independent table/control observations; source/object hashes; meaningful UI screenshots/traces; and checks failed/not run. No raw payroll/credential data belongs in a public artifact.

Exercise HTTP into the actual Worker and PostgreSQL for authority/transaction behavior. Browser checks cover human evidence review, focus, errors, narrow layout and actual 200% zoom. MCP checks use real JSON-RPC transport and schema/permission behavior. Use maintenance access only for fixture setup, deliberate fault injection and independent observation, not as the caller whose permissions are being proved. Test Bun composition separately where portability is claimed.

Ordinary rollback, killed process, rejected connection, cancellation, commit-response loss and competing first attempts are distinct scenarios. One passing replay after commit is not evidence for all of them. Structural validators and static checks remain necessary but cannot verify tax meaning, legal applicability or provider acceptance.

## Plan validation versus product validation

The planning artifact is checked for: all seven specifications present; each packet has owner/context, dependencies and acceptance; all dependency IDs exist; no mandatory dependency cycle; every E-01–E-21 scenario is referenced; local links resolve; shared monetary/authority/phase contracts agree; external facts have owner/gate/acquisition output; and no production/test changes were made by this planning task.

[Planning integrity](evidence/planning-integrity.json) records those document/index checks. It does not claim execution of the proposed scenarios. A manual self-review additionally checks failure paths that a link checker cannot assess: half-corrections, ambiguous import identity, two residual authorities, false readiness, circular runtime close/tax logic and restored obsolete-writer authority.

The self-review made two concrete consistency fixes: ADR 0004 and the maintained domain contract now retain the implemented paired money fields; OPS-06 treats connected filing as an applicability gate instead of an unconditional engineering dependency. Tax-bridge calculation explicitly precedes final close at runtime even though its engineering packet consumes the close machinery. These are planning decisions awaiting implementation/proof, not defects claimed against a tested release.
