## Purpose and disposition

A comparison finding identifies a behavior worth examining. It is not automatically a new implementation owner. Before dispatch, resolve it to an existing core operation, a profile extension, a helper, an explicitly conditional case or a recipe that must be rejected/rederived. The target implementation is evaluated independently; reference presence is not correctness and absence from a narrow source read is not proof of absence everywhere.

The revised table is the working scope decision for each retained ID. The exact original full text remains available in the pinned reviewed commit; original prerequisite values and proposed changes are recorded side by side in `parity-register.json`. The existing mandated packet numbers and historical core count are not renumbered.

## A/B/C classification, clarified

**A: mechanism.** Independently reviewed deterministic computation, parsing or data-structure behavior with explicit preconditions, limits and expected outputs. A does not mean verified by default.

**B: rule-bearing behavior and data.** Format grammar, computation/aggregation order, rounding location, date/threshold semantics, official identifiers and dated values. Port the structure only after the normative specification is identified; replacing a rate cannot fix an incorrect formula.

**C: eligibility and judgment.** Which treatment, authority, identity, recovery right or reporting obligation applies to the facts. Re-derive from the applicable source and reviewed facts.

Product ranking, thresholds, two-pass extraction choices and acceptable operational risk are explicit product/evaluation policies. They are neither legal facts nor self-proving A algorithms. Mixed rows are decomposed inside their existing owner, with their B/C inputs named before they can be activated.

## Corrected safety boundary

Required financial check unavailable -> affected execution blocked. Unknown source meaning -> retained evidence and explicit admission limitation. Search cap -> incomplete scope, not proof of no match. Small difference -> case or qualified adjustment, not a plug. Exact amount match -> candidate evidence, not payment/recognition authority. Zero net cash -> omit a payment instruction, not all accounting. Signing, submission and authority acceptance -> distinct revision-bound records.

The R1-R25 prescriptions in [RULE-CORRECTIONS.md](RULE-CORRECTIONS.md) supersede the unsafe or underspecified recipes for this proposed revision. Source algorithms behind the original comparison are not independently verified by this review.

## Minimal executable slice contract

Every dispatched slice, whether a whole PRY row or a child such as PRY-03/Fortnox, includes:

```text
id and stable parent finding
canonical operation owner and exact target files/commit
observed existing behavior versus proposed delta
finite input/profile scope and complete output
pure computation + typed failure/unknown/ambiguity results
financial/nonfinancial group and tx-passing persistence effects
approval, replay, economic identity, correction and external-outcome semantics
source/format/rule references and component A/B/C classification
independent example + edge + failure + concurrent/replay acceptance cases
actual permitted checks and separate missing proof/company/provider gates
```

Do not create a new generic specification engine to represent this. A concise Markdown card and a small register row in the current docs are sufficient. Model-generated code does not obtain approval or factual authority from being generated inside that card.

## Stage-specific evidence

A proposed leaf needs a coherent contract and proof plan. An implementation needs the actual source/compiled interface. A financial acceptance case needs exact expected journal/register effects and observed transaction behavior. A released legal/format profile needs the applicable primary input bundle. Connected acceptance needs real provider evidence. Company readiness needs complete actual input/control coverage. These statuses may differ; never overwrite them with one completion checkbox.

Preserve IDs, original findings, revised scope decisions and dated implementation/proof records. Do not delete a finding on completion or replace its historical requirement text with a vague success claim. Reinspect source movement before dispatch and record what changed.

Run the existing core checker as authorized for its own scope.
