# 0011: Reference parity, ownership and rule qualification

**Status: proposed replacement of the accepted planning decision for review.** This file does not itself change repository authority or activate an implementation, rule or provider. Target of review: `ac9e1a918d86c6872f415e3a988cbc7d25b6f9fb`.

## Context

Reference comparison can reveal useful behavior and missing edge cases. A reference's source presence, age or apparent maturity does not establish correctness. A deterministic formula can encode dated policy or a wrong legal assumption; even refusal behavior needs review before it becomes a target requirement.

The core 53-packet delivery index is an existing planning scope, not a count of all product features or all company-release obligations. Reference findings overlap its owners and supplemental requirements. Duplicating them as independent implementations creates competing authorities; excluding them from every readiness dependency can conceal an applicable blocker.

## Decision

1. Preserve `PRY-01` through `PRY-85` as stable comparison-finding identifiers, separate from the mandated core namespace. Do not renumber or delete a finding merely because its implementation owner already exists.
2. Resolve each finding to an existing canonical owner, a genuine new profile/capability, a deferred conditional case or a rejected/uncertain recipe. An unimplemented behavior can already have a valid owner. Never equate “not implemented” with “not planned”.
3. Record exact reference and target evidence: repository/revision/file/symbol/range, inspected target operations and the concrete delta. When this evidence is missing, label the comparison unverified rather than declaring absence or validated parity.
4. Classify each component under A/B/C. A covers independently reviewed mechanisms; B covers normative formula shapes, order, formats, thresholds and dated data; C covers applicability/legal judgment. Product heuristics carry explicit evaluation/policy evidence rather than disguised statutory status. No class is an automatic correctness certificate.
5. Preserve correct refusals and reject unsafe reference behavior. Required financial-check failure is never permission to commit. Do not balance missing source history, remove real bank movements from independent controls or use confidence alone as authority.
6. Use application-owned Effect operations, scoped tx-passing persistence and narrow PostgreSQL integrity. Reuse the established queue/outbox, evidence, tax, commerce and reporting owners. Parity never authorizes a second ledger, policy engine or queue framework.
7. Keep the core index's historical metric separate from supplemental-disposition metrics. Maintain an explicit combined readiness/gate view for every selected release. An applicable PRY prerequisite can block release without changing the historical core denominator. Its dependency must be machine-visible, not hidden in prose.
8. Distinguish contract, implementation, qualified rule, external-access and actual-company gates. Offline/public-input development does not require unnecessary live credentials. Connected acceptance never follows from a local adapter or simulated response.
9. Require each executable slice to name its full supported journey, financial/nonfinancial effects, correction/recovery consequences and independently specified acceptance cases. No source checkbox or documentation validator establishes runtime behavior.

## Consequences

The PRY backlog is a traceable inventory feeding existing owners, not 85 mandatory standalone projects. Large provider/payroll/profile rows can have scoped child slices under the same finding ID without replacing core ownership or hiding partial completion.

Original comparison text, revised decisions and implementation evidence remain historically accessible. Do not replace the original requirement with a green status that erases what was expected. Unsupported but applicable behavior remains visible through release gates.

No source constants or third-party code/data are automatically reusable. Follow the repository's licensing posture and retain required provenance. This decision does not create a new legal interpretation of any upstream licence.

## Validation

Run the existing core-plan checker where authorized and preserve its scope. Add or propose a supplemental planning validator for PRY identity, reference fields, owner links, component classes, typed stage dependencies and applicable release gates. Check the union of release dependencies without treating `refines` as a precedence edge.

Document validation is not financial proof. Actual calculations require independent expected outcomes; transaction behavior requires permitted real PostgreSQL/application cases; artifacts/providers require their own qualified contracts and observed outcomes. Test additions and external/production actions retain their existing explicit authorization requirements.
